# Безпека ефіру та аварійні протоколи

Версія протоколів: `2026.08-safety-v1`.

Цей контур не використовує LLM. Тексти для технічних збоїв, виправлень і блокування непідтверджених даних є детермінованими, а кожна подія записується в SQLite-таблицю `broadcast_events`.

## Watchdog тиші

Watchdog активний лише коли ефір запущено. Свідома пауза оператора та заблокований браузером autoplay не вважаються аварією.

- через 2–3 секунди без активного локального плеєра або TTS створюється `silence_warning`;
- через 5–8 секунд запускається `dead_air`;
- спочатку система намагається відновити поточний локальний файл;
- далі переходить до наступного локального треку;
- якщо музичного резерву немає, звучить коротке повідомлення про технічну паузу;
- спосіб відновлення записується як `silence_recovered`.

Пороги налаштовуються в UI. Поточний детектор перевіряє стан каналів відтворення, а не фактичний рівень сигналу на звуковій карті. Для production-потоку ще потрібен незалежний signal-level detector після мікшера.

## Протокол виправлення

Кнопка `Виправлення` вимагає п’ять полів:

1. що саме прозвучало неточно;
2. правильне формулювання;
3. назву джерела;
4. повний HTTP(S) URL;
5. відповідального редактора.

Без цих даних репліка блокується. Готовий текст прямо називає неточність, дає правильну інформацію та джерело, не виправдовується і не використовує гумор. Після озвучення подія переходить зі статусу `queued` у `aired`.

## Аварійні стани

| Подія | Автоматично | Поведінка |
|---|---:|---|
| `dead_air` | так | відновити файл → наступний локальний трек → технічне повідомлення |
| `technical_pause` | так/оператор | коротко повідомити без вигаданого часу відновлення |
| `guest_drop` | ні | один раз назвати втрату зв’язку й перейти до резерву |
| `unconfirmed_fact` | ні | не озвучувати до редакторської перевірки |
| `abusive_listener` | ні | не передавати повідомлення в TTS, зберегти мінімальний журнал |
| `safety_alert` | ні | вимагати офіційний текст, HTTP(S) джерело й редактора |
| `correction` | ні | озвучити простежуване виправлення без гумору |

Safety alert не може бути створений лише на підставі AI-тексту. Система пропускає в ефір рівно переданий офіційний текст після заповнення джерела й відповідального редактора.

## Журнал

Для кожної події зберігаються тип, критичність, статус, деталі, ефірний текст, URL джерела, редактор, час створення та час закриття. API повертає останні події, кількість відкритих виправлень і критичних інцидентів.
